# i18n Message Handling and Audit

**Languages:** [繁體中文](../zh-TW/i18n技術說明.md) · [English](i18n技術說明.md) · [日本語](../ja/i18n技術說明.md)

## Scope

This scan covers the Git-managed source code in `core/`, `server/`, `web/`, `cli/`, `bin/`, `scripts/`, and includes non-ignored new files in subsequent audits. Dependency packages, build output, test expected values, development documentation, author-written story/knowledge content, character names, model labels, URLs, program identifiers, and raw external-process logs are not treated as translatable UI strings. No `.env` file was read or modified.

All translations are kept in the existing `web/locales/ja.json`, `zh-TW.json`, `en.json`. The sections, keys, and data types of the three files are completely identical; every item uses a semantic English key corresponding directly to the translation string, e.g. `"invalid_requestId_format": "requestId 格式不正確。"`, with no `source`/`text` wrapping and no sequence-number keys. `{0}`, `{1}`, etc. are parameters. No separate JSON holding all languages is created. The compatibility layer for existing text calls is compared against the Traditional Chinese translations and the other languages' translations; the handful of existing API original strings that differ from the translations are mapped by `core/service-i18n.ts`'s `sourceAliases` to the same semantic key — this is not a separate translation catalog.

## HTTP and SSE

After routing and request deduplication/result storage, `server/http.ts` translates the returned content via `server/response-locale.ts`. `core/service-i18n.ts` handles only the designated service fields: top-level error/notice, AI health status message, publishing-job message, image-generation history notice, knowledge-base error, Twitter system notifications, and image status display text.

- It does not traverse/translate game save files, player posts, comments, LLM conversations, character names, image URLs, or captions.
- Core exceptions keep their original stable text, with translation concentrated at the output boundary; therefore cancellation, retry, caching, and persistence do not depend on the interface language. You cannot judge a missed translation by the mere presence of a Chinese `throw Error` in the source; you must check whether its original text is in the catalog and in the actual HTTP response.
- Use full message/full template matching, not fragment substitution of API content. Known errors keep their HTTP status code, field names, limits, and other parameters; unknown native/vendor exceptions return a localized generic error without directly leaking keys or paths from the original exception.
- JSON, plain-text errors (including responses for which Bun has not yet set a Content-Type), and SSE are all handled. SSE is translated frame by frame, preserving `id`, `event`, `retry`, and comments; split UTF-8 and CRLF do not affect parsing.
- Language priority uses `X-Makeine-Language`, then `Accept-Language`; unsupported languages default to Japanese. EventSource cannot carry custom headers, so `/api/game?events=1&language=...` additionally supports a language parameter, and switching language rebuilds the subscription. The language is captured at stream creation to avoid a background event reusing another request's language.
- In old Twitter save data, `imageStatus` is simultaneously a status-determination value and must not be translated. The API additionally provides `imageStatusLabel` for the interface, while retaining the `twitterPostPending` determination.

## Frontend and CLI

The existing interface still uses the `legacy-i18n.ts` compatibility layer; the new service catalog matching runs before the kanji check, fixing the problem that English errors and accessibility text such as Close, Loading could not be translated. Dynamic `aria-label`, `title`, and `placeholder` updates are re-translated and separately record the original text and the last-applied value, so switching language does not lose the original. `data-i18n-skip`, textarea, editable content, script, and style are not handed to DOM translation; Twitter posts/comments and LINE non-system messages are already marked for skipping.

The frontend adds a language header only to same-origin requests, preserving the existing Request headers, and does not forward it to external services.

The CLI likewise reads the `cli` section of the above three files; at development time it reads `web/locales`, and at build time it copies the same three files to `dist/locales`; there is no independent CLI translation source. Startup/update/help output uses `cli/i18n.mjs`, with the language determined by `MAKEIN_LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, and the system locale; `ja`, `en`, and `zh-Hant` are supported, and system formats such as `zh_TW` are also accepted. The CLI has no browser localStorage, so the language must be specified separately.

## Verification and Adding New Messages

Run `bun run audit:i18n` to check whether the direct error strings, templates, and validateContent assert messages in the API/core have a catalog mapping. `bun scripts/audit-i18n.ts ui`, `server`, and `english-ui` provide candidates for manual review; candidates include identifiers, JSX line breaks, and author content and must not all be translated mechanically. The audit does not call an external translation service.

`tests/service-i18n.test.ts` checks tri-language/parameter consistency, actual HTTP routes, health-status caching, invalid JSON, media 404, SSE splitting and event IDs, request-language isolation, CLI, status semantics, and that data is not modified. Also run `bun run check`, `bun run test`, `bun run build` (`bun run test` already includes `--timeout=40000` because postgres.js is slow).

When adding a new API message, add the same semantic key and the complete translation for each language to the three catalogs; do not concatenate sentence fragments. If you need to keep an old API original string that differs from the tri-language translations, add `sourceAliases`. When adding a new service field, you must explicitly add it to the output-field whitelist; do not translate every field named text/message. Static scanning cannot prove all arbitrary dynamic string-building paths, so add behavioral tests for new templates and API outputs.
