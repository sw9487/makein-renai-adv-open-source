# Dynamic Event Performance

**Languages:** [繁體中文](../zh-TW/llm-scene-performance.md) · [English](llm-scene-performance.md) · [日本語](../ja/llm-scene-performance.md)

The game entry currently requires a working LLM API to be configured first; `/api/ai-status` checks the model list first, and there is no formal "skip AI and keep playing" flow. Encounters, mainline events, in-class encounters, after-school home routines, and post-choice responses use `present_scene` to generate the current narration and specific response text. The prompt includes real-time character identity, date, location and calendar state, affection, shared memories, available supplementary knowledge, and the previous scene; when Web Search is enabled, it can be queried on demand.

Daily routines can create various small events; the mainline preserves the existing event facts and consequences. Choices retain their affection changes, flags, response constraints, and listening intent by original index, letting the model design only the current specific expression. The model cannot directly write the save file, skip dates, or modify routes.

Listening options require the first line to be a line the character actually speaks, and summaries cannot replace dialogue. No additional options are generated; the player can continue free chat. The existing occasional-choice and cooldown rules for character chat remain unchanged.

The 21 built-in characters each have an original `normal` and 9 transparent-background PNG expression sprites: `happy`, `angry`, `sad`, `surprised`, `shy`, `suspicious`, `crying`, `enduring`, `cold`. The files are registered under each character's `sprites` in `content/game.json`, with actual files in `content/assets/`. Face-to-face dialogue's `present_character_reply` / `present_character_choices` and dynamic scene's `present_scene` pass the character's actually-configured expressions to the model as an optional enum; the `expression` chosen by the model is saved together with the line and switches the sprite. LINE does not display sprites and provides only `normal`. Old saves that still use the built-in original sprites are backfilled with the new expressions on load; manually replaced sprites or expressions are not overwritten. Transitions preload the sprites to be shown before fading in.

Character responses in LINE and face-to-face free chat can carry 0–3 ordered `actions`, currently supporting `twitter_follow`, `twitter_unfollow`, `twitter_post`, and `line_message`. These are executed one by one by `server/character-actions.ts` and follow Twitter's private follow-request / block rules; a spoken line does not equal an executed action. The whole conversation is first processed against a copied game state, and if any action is invalid the current turn is not committed. When community apps are disabled, the corresponding actions are not exposed to the model and must not be executed. The legacy single `twitterPost` field is still readable, to avoid invalidating results from compatible models.

Only after the scene is generated successfully is it committed together with the game operations. If tool format errors, service failures, or cancellations occur, the original progress is preserved, and retries must re-run the corresponding API rather than replay old failures. Generated results are stored in the conversation, so refreshing and loading a save do not re-roll; the original draft is only restored after the Editor modifies the original event. Pressing "Start New Story" enters a fade-out, and the black screen waiting for the API shows a loading indicator; after choosing one of three, the options disappear immediately without waiting for the next page to finish generating.

Tests use a mock API and verify proactive openings, context-tool payloads, preservation of choice consequences, prohibition of extra options, and that navigation does not trigger generation. The main implementations are in `server/game-api.ts`, `server/chat.ts`, and `core/navigation.ts`; regression tests are in `tests/scene.test.ts`, `tests/navigation.test.ts`, and `tests/scene-time.test.ts`. Text quality still depends on the model the user has chosen; structural validation cannot guarantee that every narrative detail matches the original work.
