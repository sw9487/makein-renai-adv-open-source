# Twitter 技術說明

**言語:** [繁體中文](../zh-TW/Twitter技術說明.md) · [English](../en/Twitter技術說明.md) · [日本語](Twitter技術說明.md)

最終確認: 2026-09-11。これはゲーム内の仮想コミュニティであり、実際の Twitter に接続・公開されることはない。本ドキュメントは現在のプログラムに基づき、開発者がスケジュール、ツール、権限、UI、セーブデータの挙動を追跡できるようにするものである。予定された機能を列挙するだけではない。

## 1. モジュールとデータ所有権

| ファイル | 責務 |
| --- | --- |
| `core/twitter.ts` | コミュニティ型、デフォルトの相互フォロー、キャラクターのコミュニティ設定、閲覧権限、プレイヤーデータの投影、通知フィンガープリント、オンライン／入力状態 |
| `server/twitter.ts` | HTTP 操作、LLM 判断、スケジュール、提出重複排除、相互フォロー、画像公開、Twitter → LINE 反応 |
| `server/http.ts` | `/api/twitter` の GET／POST／PATCH ルート |
| `server/proactive-line.ts` | ゲーム時限の提出時に `startTwitterSlot` を呼び、成功後にスケジュールを開始 |
| `server/game-api.ts` | スケジュールの復元、新しい物語、セーブデータ読み込みのライフサイクル |
| `server/repository.ts`、`server/concurrent-state.ts` | 永続化、compare-and-swap、他のゲーム操作との統合 |
| `server/stable-diffusion.ts` | 画像ツール解析、純物限定、共有 SD 実行入口 |
| `server/image-queue.ts`、`server/image-history.ts` | 画像生成キュー、画像ジョブ記録 |
| `web/components/twitter-panel.tsx` | トップ／探索／個人ページ／通知／スレッド、操作とポーリング |
| `twitter-account.tsx`、`twitter-typing.tsx`、`twitter-upload.tsx` | アバターのオンライン緑色ドット、入力アニメーション、画像添付アニメーション |
| `web/components/twitter.css` | 明暗色、レイアウト、有限インデント、アニメーション、モーション削減設定 |
| `web/locales/{zh-TW,ja,en}.json` | モデル命令と新規 UI 文言 |

正式なデータは現在のプレイヤーの `GameState.twitter` に保存され、フロントエンドの一時配列ではない。LLM はデータベースを直接変更せず、ツール引数を返すだけであり、バックエンドが再検証・提出する。

### 主要フィールド

- `accounts[id]`：handle、private。キャラクター設定から再構築される。プレイヤーの非公開状態は別途 `playerPrivate` に保存され、人物のデフォルトより優先される。
- `following[actor][target]`：有向フォロー関係。`true` のときのみフォローとみなす。解除後は `false` が残る場合がある。
- `requests[target][applicant]`：審査待ちのフォローリクエスト。処理後は `false` に設定される。
- `requestVersions[target][applicant]`：新しい申請ごとの UUID。フロントエンドには公開されない。解除して再申請するとバージョンが変わり、未解除の同一申請を再送してもバージョンは変わらない。古いセーブデータには安定した legacy 識別子が補完される。
- `posts[id]`：本文、作者、ゲーム日付／時限、実時間の並び順 `created`、画像、`replyTo`、いいね、リポスト。
- `jobs[id]`：actor、元の日付／時限、due、読める候補スナップショット posts、status、trigger、error。
- `online`／`onlineSlot`：この時限のオンライン者。ジョブが完了してもオフラインになるわけではない。
- `npcInteractionLimit`／`npcInteractions[slot]`：デフォルト 3、0〜20 で調整可能な NPC 即時相互上限。
- `follows`／`unfollows`：相互フォローとフォロー解除の反応イベント。handled で重複処理を防ぐ。
- `threadSeen[actor][root]`：オフラインでのスレッド補完のタイムスタンプ。
- `operations[requestId]`：プレイヤー操作の意図。リクエスト再送による重複投稿や二重切り替えを防ぐ。
- `typing`：対外投影時にのみ計算され、独立して永続化される「フェイク入力」スケジュールではない。

`imageSession` は画像添付ジョブが属するプロセス／run の内部識別子で、フロントエンドには返されない。`jobs`、`operations`、follow/unfollow イベント、相互カウントなどの内部状態もフロントエンドには渡されず、UI は権限でフィルタされた投稿と必要なコミュニティデータのみを受け取る。

## 2. 時限開始とオンラインスケジュール

```text
新規ストーリー／日付または時限を進める／GET が不足したリストを修復
  → twitterState：初期化、デフォルトネットワーク、キャラクター設定を読み込む
  → startTwitterSlot：オンラインリストを決定して保存
  → 各人に base ジョブ + discovery ジョブ + 任意の catchup ジョブを作成
  → セーブ成功後に resumeTwitter
  → due になったら runTwitterJob
  → fresh-state 検証 → LLM → fresh-state 提出 → 他のオンラインキャラクターを起こす
```

候補は「ゲーム時間で既に登場した」すべての NPC であり、プレイヤーが知っている人に限らない。未登場が未認識を意味するわけではない。各人の基本確率に低／中／高の活発度ウェイト 0.4／1／1.5 を掛け、さらに少なくとも 6 人を補い、うち少なくとも 4 人は既知の者とする。候補が不足する場合は実際の人数を取る。

通常のジョブは約 5〜50 秒の遅延。友好ジョブは約 2 秒。即時反応は約 0.5〜2 秒で、モデルとキューの時間が加算される。これは毎秒強制的に投稿を生成するものではない。時限リスト、ジョブ ID、完了状態は保存される。空リストの修復時は既存のジョブを先に探し、すでに完了した同時限のジョブを再送しないようにする。

同一キャラクターが running ジョブを既に持つ場合、他のジョブは遅延する。異なるキャラクターは並行できる。`activeJobs` は同一プロセスで同一タイマーを再スケジュールするのを防ぐ。プロセス再起動後、scheduled ジョブは復元され、実行中だった running ジョブは interrupted として標示され、支払い済みの可能性があるモデルリクエストを自動的に再送しない。ゲームがすでに終了している場合は、保留中のジョブを実行しない。モデル待機中に終了した進捗は、新しいコミュニティ行動を提出しない。

### オンライン緑色ドットと入力アニメーション

右側の「知っている人」はオンラインキャラクターを優先して表示し、緑色ドットはアバターの右上にある。「0 人がオンライン」は表示しない。相互上限に達しても緑色ドットは消えない。

`twitterView` は、この時限の running、対象が見える、キャラクターが既知かつオンラインである post／reply／catchup ジョブのみを `typing: [{actor, postId}]` に投影する。フロントエンドはその投稿またはコメントの下に名前と三点アニメーションを表示し、複数人は結合して表示する。完了、アイドル、いいね、リポスト、失敗、中断、権限消失のいずれでも削除される。アニメーションを演出するためにリクエストを余分に遅延させることはない。

モデルは同一リクエスト内で行動を判断しテキストを生成するため、「入力中」はこの内容を処理中であることを意味し、最終的に必ずテキストが送信されるとは保証されない。base の自主ブラウズで対象が未確定の間は、入力状態を勝手にどこかの投稿へ紐付けない。パネルは 1.5 秒ごとにポーリングし、ページ非表示時は省略し、単一ポーリングは重ならない。非常に速いリクエストは画面に捕捉されない場合がある。アニメーションは `prefers-reduced-motion` を尊重する。

## 3. LLM ツールとソーシャル判断

唯一のコミュニティツール `twitter_action` は、有効な tool call を一度だけ返さなければならない。

```json
{"action":"reply","target":"フォーストまたはコメントのID","text":"返信内容","image":false}
```

| action | target | バックエンドの効果 |
| --- | --- | --- |
| idle | 空文字列 | コミュニティ内容を変更しない |
| post | 空文字列 | トップ投稿を作成 |
| reply | 直接返信するメッセージ ID | replyTo 付きの新メッセージを作成し、コメントを誤ってルート投稿に付けない |
| like | メッセージ ID | NPC を「いいね済み」に設定。プレイヤーは切り替え可 |
| repost | メッセージ ID | NPC を「リポスト済み」に設定。プレイヤーは切り替え可。非公開スレッドは拒否 |
| follow／unfollow | アカウント ID | 公開は即時フォロー、非公開はリクエスト送信。または関係／リクエストを解除 |
| accept／decline | 申請者 ID | 自分宛の既存リクエストを処理 |
| delete | 自分のメッセージ ID | 自分のトップ投稿またはコメントを削除 |

本文は最大 280 文字。post／reply は空欄不可。post／reply のみが画像添付を要求できる。モデルの HTTP が非成功、切り詰め、誤ったツール、複数ツール、不正な action、未読みの相互対象のいずれの場合も提出しない。提出時に権限を再度確認し、LLM 生成中にデータが変わったからといって制限を迂回できない。

NPC ペイロードには、キャラクタープロンプト、即時身分、日付／時限、オンラインリスト、アカウントデータ、followCandidates、既存のフォローとリクエスト、プレイヤーへの好感度、個人記憶、読める投稿が含まれる。通常のブラウズはジョブ作成時の候補スナップショット（最大 35 件）を使用する。明確な議論対象を持つ反応ジョブは、ルート投稿とスレッド全体で見える子孫コメントを created 順に提供する。

各有効なローカル添付画像は投稿 ID でラベル付けされ、ファイルパスを単なるテキストとして渡すのではなく、マルチモーダルな `image_url` に変換される。存在しない、またはローカルの正当なメディアパスでないものは添付されない。`detail: low` が現在の画像入力設定であり、モデルは画像に対応する必要がある。非常に長いスレッドにはまだ追加の意味要約やトークンの自動切り詰めはなく、モデル側のコンテキスト容量が依然として制限となる。

### 自主的な友好関係と相互フォローは別機能

discovery は各オンライン者の独立した LLM ジョブであり、「今回はもう投稿した」ことによって消費されない。候補は未フォロー、未交流、まだ自分をフォローしていない他の NPC を優先し、公開の概要と共通アカウントを提供する。プレイヤーの met でフィルタはしない。このジョブは follow／accept／decline／idle のみができ、follow 対象が候補集合にあることを検証する。

主動的な相互フォロー switch は確定的な選好である。有効な新しいフォローを受け取ると、キャラクターが次にジョブを実行するときにイベントを確認し、有効なら相互フォローする。非公開対象には引き続きリクエストを送り、直接承認はしない。解除済み、フォロー済み、審査待ちリクエストが既にあるイベントはやり直さない。switch がオフの場合に、LLM が自然に相互フォローするとは保証されない。

LLM の accept／decline を提出するとき、同一の CAS で、現在も審査待ちであること、モデルのスナップショットにその申請が確かに存在すること、requestVersions が同じであることを確認する。解除後の新規申請には古い LLM 判断を受け付けない。期限切れのジョブは関係、記憶、審査通知を変更せずに終了する。フォロー反応のスケジュールは申請バージョンで区別し、新規申請を古い scheduled／running ジョブと統合しない。未実行の期限切れ申請ジョブは直接スキップし、モデル呼び出しを無駄にしない。

NPC のプレイヤーへの非公開リクエストには好感度ハードルがある。未達なら accept を禁止する。現行プログラムは達した decline を accept に変更する（プロンプトだけでなく）。モデルは他の行動や idle を選ぶこともできるため、即時承認を約束するものではない。自分宛のリクエストのプレイヤー審査は「申請者未認識」制限の対象外であり、未知の NPC のリクエストが永遠に処理されない事態を防ぐ。

### 反応の種類と継続的なコメント

新しい投稿はオンラインのフォロワーを起こす。新しいコメントはルート作者、直接の対象、スレッド参加者を起こす。有効な `@` は言及された者を起こす。いいねは元作者へ通知。リポストは元作者とリポスト者のオンラインフォロワーへ通知し、情報がソーシャルサークルに沿って伝わるようにする。いいね取り消し／リポスト取り消しは新しい反応ジョブを作らない。フォロー関連イベントは対象者へ通知する。非公開コンテンツも読める必要がある。プレイヤー自身は NPC ジョブに入らない。この時限の online リストが既に保存されている場合は、古いジョブの存在だけでオンラインを判定するのではなく、リストを基準にする。

`@` しなくても返信できる。各新規コメントには独立した ID があり、他のオンライン参加者をさらに起こせる。同一 NPC が同じ対象へ既に返信している場合は、送信しない。いいねとリポストも重複排除される。繰り返しの文章書き換えで提出チェックをすり抜けることはできない。対象が削除されるか、キャラクターが閲覧権限を失った場合、ジョブは終了し、trigger に保存された古い本文をモデルへ再送しない。

オフラインのキャラクターがオンラインになったとき、最も近い関連する未読スレッドを catchup として選び、他の古いスレッドは一つずつ機械的に補完するのではなく「既読」と標示する。新規コメントが created 時間を進めると、古いスレッドが再び浮上する。モデルは返信しなくてもよく、議論を自然に沈ませられる。

相互指示は明確に区別する。伝える価値のある公開情報は repost を優先評価。テキストが不要な日常の承認は like を優先。新規の質問、直接返信、明確化のみ reply を優先。これは状況選好であり、硬直した確率や割り当てではない。モデルが選ばなかったフォロー／いいね／リポストを生成しない。

## 4. 相互上限と並行性の一貫性

すべての提出は新しい読み取り状態の clone で行い、runId を確認し、compare-and-swap の失敗は最大 8 回再試行する。コミュニティ更新は revision を上げるが、元の sceneRevision は保持し、ストーリー画面への干渉を避ける。新しい物語／セーブデータ読み込みで runId が変わり、古いリクエストは新しい進捗へ書き込めない。

| 行動 | NPC のこの時限の枠を消費するか |
| --- | --- |
| 新規投稿、フォロー、相互フォロー、リクエスト処理、idle | いいえ |
| プレイヤーと NPC の間の相互 | いいえ |
| キャラクターがオンライン前から存在した投稿／コメントへの返信 | いいえ。その NPC の base ジョブの posts スナップショットで判定 |
| 過去の日付／時限の内容への返信 | いいえ |
| この時限のオンライン NPC 2 人が、オンライン後に追加されたこの時限の内容へ reply／like／repost | はい |
| 返信済み／いいね済み／リポスト済みの重複提出 | いいえ。実行しない |

枠は同一プレイヤーの進捗、同一時限の NPC が共有する合計であり、各自 3 回ではない。ペイロードの interactionBudget は limit、used、remaining、limitedTargetIds を提供し、モデルが提出できない相互を事前に避けられるようにする。完全なコンテキストがこれによって切り詰められることはない。カウントとコミュニティ行動は同一の CAS で行い、残高がなければ idle に変更し、超過して減算することはない。上限に達してもプレイヤーが会話を続けることは妨げない。画像添付の返信は、公開待ちメッセージの作成時点でその行動枠を既に消費し、他者は画像公開後にのみ相互できる。

## 5. 画像公開と純物ツール

```text
post/reply(image=true)
  → 作者に見える pending メッセージ + アップロードアニメーション
  → 画像プランニング LLM → ツール／tags／LoRA を検証 → SD キュー
  → 画像保存成功 → アトミックに画像添付、pending 解除、記憶書き込み、オンライン者を起こす
  → 確定的失敗／プロセス間中断 → 失敗と標示、本文を保持し純粋テキストを公開
```

pending 中は他者は読めず、NPC の判断も自分の pending 内容を除外し、相互記憶の事前書き込み、いいね、返信、リポスト、新規投稿通知を行わない。画像と本文が一緒に読めるようになってから反応を発火する。削除または run 変更後に戻ってきた画像は投稿を再作成しない。

`imageSession` はプロセスと run に紐付く。サービス再起動やセーブデータ読み込み後に持ち主を失った pending 画像は、明確な失敗テキスト投稿に変換され、永遠にアニメーションで固まらず、有料の画像生成を自動的に再送もしない。これは失敗の縮退であり、画像があると偽らない。

- LINE 純物ツール：`generate_object_image`。
- Twitter 純物ツール：同じ `generate_object_image` とパーサー。
- 人物ツール：LINE の `generate_image`／Twitter の `twitter_image`。人物 tags に対応したキャラクターのみ提供される。ツール出力は実際に提供された名前でなければならず、無効化された人物ツールを自ら呼んではならない。
- 純物には loras フィールドがない。渡すと拒否される。正側は `no humans, still life, object focus` を強制し、人数、加重人物タグ、髪色、人体部位などを除外。負側は人物、顔、手、身体、背景人物、反射タグを強制。SD に送る前に objectOnly プランを再度確認する。
- 本文で誰かに言及しても、その人が映るとは限らない。お菓子、デザート、試験用紙、ランドセル、書籍、トロフィー、メダルは物品ツールを使うべき。人物と物品の同フレームを明示的に要求した場合のみ人物ツールを検討する。
- LINE／Twitter／ストーリーは安全実行キューとメディア保存を共有するが、各画像は UUID を使用し、上書きされる固定ファイル名は共有しない。三つの相互に隔離された SD 実行プロセスではない。

tags 制限は生成後の視覚的レビューの代わりにはならず、現在自動人物検出器はない。ベースモデルがプロンプトに従わない場合もある。画像失敗はプレイヤーの本文を削除せず、SD の全体設定も変更しない。

## 6. 権限、記憶とデフォルト関係

`canReadPost` はすべての祖先を層ごとに確認し、循環／欠落祖先は不可読とみなす。公開コメントは非公開のルート投稿を漏らしてはならない。非公開アカウントまたは非公開祖先を含むスレッドはリポストできない。トップ投稿を削除すると、その子孫は保存上残るが祖先を失ったため不可読となり、他の作者のデータは連動して削除されない。

プレイヤーは追加でゲームの認識／フォロー規則の影響を受ける。未認識のキャラクターは背景で投稿や友好関係を行えるが、プレイヤーには直接表示されない。認識してフォローすると過去の内容を読める。フォロー中のアカウントがリポストした「既知、公開、未フォロー」の作者もトップに現れ得る。未認識または非公開の作者がこれによって権限を超えて露出することはない。

自発の投稿、返信、いいね、リポスト、フォローなどは、関連キャラクターの `memories` の `channel: twitter` に書き込まれ、既存の compactMemory で管理され、LINE／ストーリーで使用される。`@` と返信の受信者は、そのメッセージ全体を読める場合のみ本文へ書き込み、非公開コンテンツが記憶を通じて権限を迂回しないようにする。削除済みコンテンツは、他者が過去に合法的に読んだ記憶を消さない。

## 7. HTTP とフロントエンド操作

| ルート | リクエスト／レスポンスの要点 |
| --- | --- |
| GET `/api/twitter` | プレイヤー cookie。必要に応じてこの時限のスケジュールを修復。twitter、revision、runId を返す |
| POST `/api/twitter` | 同一ソースチェック。runId、requestId(UUID)、action、target、text、image。最新の view／revision／runId／notice を返す |
| PATCH `/api/twitter` | 同一ソースチェック。runId、任意の playerPrivate、npcInteractionLimit。最新の状態を返す |

プレイヤー身分なし 401、進捗なし 404、操作エラー 400。ルートで対応するメソッドは HTTP ルーターに明記されている。決定的な操作（いいね、リポスト、フォロー、審査、削除、設定）は LLM を経由しない。プレイヤーの投稿／コメントは現在もツールで確認され、プレイヤーが指定した本文は書き換えない。

パネルは revision で遅れて届いた古いポーリング応答を無視し、runId で他の進捗の応答を拒否する。操作は同一 requestId を安全に再送できる。いいね／リポストは「LLM 経由で提出」という文言を表示しない。

コメントは replyTo で直接の関係を表し、探索ではルート作者を注記する。コメントページのタイトルは「コメント」で、戻る矢印はルート投稿へ戻る。ページには返信ボックスと画像添付トグルがある。深いスレッドはフラットに展開し、最大の視覚的インデントでどんどん狭くならないようにする。自分のコメント／投稿の削除は内部の確認ウィンドウを使用し、いいね／リポストとフォローリストは内部のアカウントウィンドウを使用する。

`@` 入力はフォロー中の友達リストを提供し、上下キーで選択、Enter で確定。日本語／中国語の IME 変換中は Enter を遮断しない。公開の有効な handle は青字とホバーカードを表示し、長いアカウントの部分プレフィックスを別の人物と誤認しない。

Escape は候補を閉じるだけでなく、選択項目をリセットし、入力を続けると再度開く。中国語の句読点の後でも `@` を開始できる。操作中またはゲーム終了後は、コメント返信操作を開始しない。

通知には、フォローリクエスト、notice、フォロワーの新規投稿、`@`、自分の内容への返信／いいね／リポストが含まれ、対応ページへジャンプできる。シーンの Twitter ボタンの赤ドットは runId に対応する localStorage の既読フィンガープリントを使い、パネルを開いたときに既読を標示する。現在は「新規トークン」で未読を判定し、削除やいいね取り消しによるトークン減少で偽の新規通知を作らない。pending 画像は新規投稿トークンを生成しない。

## 8. 検証、トラブルシューティングと制限

実行:

```sh
bun run check
bun run test
bun run build
bun scripts/twitter-live-audit.ts --live
```

`--live` は設定されたモデルを使い API 量を消費するが、隔離された一時進捗を使用し、プレイヤーのセーブデータは変更しない。2026-09-11 の今回の第一ラウンドでは、モデルがいいね／リポストの両方の状況でテキスト返信を選ぶのが観測された。engagementSystem を調整した後、第二ラウンドの四つの状況で実際に能動的フォロー、いいね、リポスト、`@` なし返信が得られた。一度のサンプリングは永続的な成功率を意味せず、モデル結果をハードコードしない。

テストの要点。`twitter.test.ts` はスケジュール、権限、相互ツール、記憶、上限、重複排除、画像待機と中断、typing 投影をカバー。`twitter-http.test.ts` は実際の HTTP で PATCH とコミュニティ reset をテスト。`twitter-ui.test.ts` は実際のコンポーネントをレンダリングし、緑ドット／アニメーションの CSS を確認。`stable-diffusion.test.ts` はコミュニティ画像の共有 SD ペイロードを確認。

### ソーシャルサークル回帰スキャン

| フロー | チェックと検証 |
| --- | --- |
| ルートとプレイヤー操作 | GET／POST／PATCH、同一ソース、runId、requestId、不正ツールと操作キャンセル |
| 自主的な友好関係 | 独立した discovery、未知 NPC 候補、公開フォロー／非公開リクエスト、重複リクエストで記憶を書き換えない |
| 相互フォローと審査 | switch、イベントの一回限り処理、非公開対象リクエスト、未知申請者の審査可 |
| オンラインとスケジュール | 複数名リスト、復元、同一キャラクターの直列化、終了した進捗で背景ソーシャルを実行しない |
| 継続的な議論 | 3 人の NPC が同一スレッドでプレイヤーに応答、新しいコメントを継続、NPC 共有枠を使い切ってもプレイヤーに応答 |
| いいね／リポスト | 実ツール、提出重複排除、取り消しで NPC を起こさない、リポスト通知で元作者とオンラインフォロワーへ |
| 画像添付 | 公開待機、純物制限、マルチモーダルコンテキスト、失敗縮退、プロセス中断と古い run |
| 閲覧と記憶 | 非公開祖先、未知作者、削除、記憶の権限外アクセス不可、他システムとの統合でコミュニティ更新を保持 |
| フロントエンド | 明暗色、緑ドット／typing／upload コンポーネント、有限インデント、返信ボックス、`@`、通知導線とバージョン逆進防止 |
| 人物設定 | handle の一意性、非公開／相互フォロー switch、活発度、設定検証 |

新規の 3 NPC 統合テストは、隔離ストレージと mock LLM で実際の POST、ジョブ提出、複数ラウンドの伝播を実行する。三人全員がプレイヤーに返信し、NPC 同士は 3 回で増加が止まり、プレイヤーが再びコメントすると三人は返信できるようになる。これはスケジュールと提出規則のテストであり、モデルの自然なチャット品質の保証ではない。

今回の完全な回帰は 225 件合格、0 件失敗。型検査と正式ビルドは合格。本ドキュメントは Twitter の挙動と必要な永続化、メディア、記憶接続に限定され、ストーリー選択肢やキャラクター物語の背景実装は含まない。

トラブルシューティングの順序:

1. GET のオンラインリストが現在の日付／時限に対応しているか確認。done ジョブをオフラインと誤認しない。
2. 内部ジョブに scheduled／running／failed／interrupted があるか、error は何か。モデルの HTTP、ツール引数、画像対応を確認。
3. 相互対象がまだ存在し、祖先がすべて読めるか。pending か。
4. 同一 target への重複返信、いいね済み／リポスト済み、またはこの時限の枠が尽きていないか。
5. `twitterFollowBack` が有効か。リクエストがまだ有効か。非公開アカウントが承認待ちか。
6. フロントエンドが古い run を開いたままか。サーバーが再起動して新しいプログラムを読み込んだか。

現在利用可能なブラウザ面がないため、今回の UI 検証は実際のコンポーネントレンダリング、スタイル、データ投影のテストであり、マウス／目視の受入を偽装しない。ビルドには既存の大きなバンドル警告が残るが、ビルド失敗ではない。失敗した LLM ジョブの手動再試行 UI、非常に長い議論のトークン自動要約、生成後の人物識別はまだ提供されていない。これらの制限を「ソーシャルシミュレーションは完璧」で隠してはならない。
