# 開発ガイド

**言語:** [繁體中文](../zh-TW/development-guide.md) · [English](../en/development-guide.md) · [日本語](development-guide.md)

本プロジェクトでは、「能力の最小化、データの最小化、サーバーによる最終検証」を、すべての AI API 統合の基本ルールとしています。これらのルールはプロンプト上の提案ではなく、payload とプログラム構造に対する要件です。

## ローカル開発と実データ

プロジェクトルートから `npm ci`、`npm ci --prefix web` を実行し、続けて `npm run dev`（デフォルト 9487）で開発サーバーを起動します。フロントエンドは `vite build` で `dist/client` にビルドされ、サーバーが 9487 で提供します。`package.json` には完全なチェックコマンドが記載されています。開発用データベース、アップロード、鍵はバージョン管理の対象ではありません。Editor の保存内容はローカルのプレイヤーデータディレクトリにのみ書き込まれます。テストや実機診断をプレイヤーセーブデータに向けないでください。

> 開発環境では `compose.dev.yaml`（postgres-dev 5439、s3-dev 8334）を使用し、サーバーはローカルで Bun が稼働します。本番（`compose.yaml`）およびテスト（`compose.test.yaml`）のコンテナ、データボリューム、データベース、ネットワークとはそれぞれ独立しており、互いに干渉しません。完全な起動方法と分離の対比は[環境の区別](environments.md)を参照してください。SQLite は削除済みのため、開発前には必ず postgres-dev を起動してください。

## LLM payload ルール

1. **許可されていない能力は payload に含めない。** ある状況で画像を生成できない、検索できない、特定の種類のデータを操作できない場合は、対応する tool、tool 引数、画像、コンテキストを提供しないこと。「能力は提供しておき、プロンプトでモデルに使わせないようにする」ことで構造上の制限を代替してはなりません。
2. **今回の判断に必要なデータのみを送る。** Twitter 返信先を選ぶときはテキストデータのみを送ります。対象が確定してから、別のリクエストでその対象の単一画像を渡します。候補の投稿やコメントのすべての画像を一度にモデルへ送り込んではなりません。
3. **状況に応じて schema を組み立てる。** 通常の Twitter 操作には画像フィールドを含まないテキストツールを使用します。新規の画像付き投稿のときだけ、独立した画像投稿ツールを提供します。固定アクションには、そのアクションが実際に必要とするフィールドと enum だけを残します。
4. **独立したデータは独立したリクエストで扱う。** JSON を翻訳するとき、翻訳可能な各フィールドにつきそれぞれ 1 件の API リクエストを送ります。限定的な並列実行は可能ですが、フィールドの統合、パスの欠落、モデルによる設定全体の再構成は行わないこと。
5. **メディアはデフォルトで高コスト。** 画像、音声、大きな履歴コンテンツは、対象が選定され本当に必要な場合にのみ追加し、タスクを完遂するのに十分な最低品質・最小数にとどめます。

## 検証と失敗時の戦略

- JSON schema の `additionalProperties` は `false` にすべきです。ツールの戻り値も、サーバーが解析し、権限を検証し、現在の状態を再確認する必要があります。
- プロンプトは意味と品質だけを担い、安全境界や能力の無効化には責任を持ちません。能力の境界は payload とサーバープログラムが保証します。
- 有料または再実行不可のリクエストは、送信前にローカルで検証を完了します。状態が変更されている場合は古い結果を破棄し、失効した結果を書き戻してはいけません。
- バッチ操作で完全性が求められる場合は、まず全結果を収集し、すべて成功した後に一度に適用します。途中で失敗した場合、中途半端なデータを残してはなりません。
- ゲーム操作には `runId`、`requestId`、および必要なリビジョンチェックが付きます。モデルまたは画像が完了したときに、対象を再度確認します。非冪等な外部リクエストで結果が不明な場合は、盲目的に再送信すべきではありません。永続リクエストとイベントは `server/harness-request.ts`、`server/harness-events.ts` を参照してください。Twitter はさらに自身の API で操作を記録して重複を排除します。
- 公開／非公開コミュニティの可視性、キャラクターのメモリ、完全な作業記録は異なる境界に属します。一般的なゲームスナップショットから Twitter の生データを直接漏らしてはいけません。LINE／Twitter／ストーリーにまたがるツールアクションでは、行為者と由来を明確に記録し、コミュニティのイベントをプレイヤーの発言と誤って対応付けないこと。

## テスト要件

LLM payload に係わる変更は、少なくとも以下をテストします。

- 許可されていない tool やフィールドが実際に存在しないこと（値が `false` であるだけでは不十分）。
- 対象未選定のときは画像を含まず、選定後は対応する 1 枚だけを含むこと。
- モデルが越権した action、追加の能力、期限切れの target を返したとき、サーバーが適用を拒否すること。
- `bun run check`、`bun run audit:i18n`、`bun run test`、`bun run build` を完全に実行すること。

> テスト環境: テストは PostgreSQL テストデータベース（`compose.test.yaml` 参照、ローカル 5450 ポート）に依存し、`tests/bootstrap.ts` が `MAKEIN_TEST_DATABASE_URL`（デフォルト `postgresql://admin:105114@127.0.0.1:5450/MAKEIN_TEST_DB`）で接続します。`bun run test` には `--timeout=40000` が含まれています。postgres.js が遅く、接続 desync の回復により web-search などのケースが Bun のデフォルト 5 秒を超えるためです。直接 `bun test ./tests` を実行するとこの引数は付きません（Bun 1.3.14 は `bunfig.toml` の `[test].timeout` を無視します）。テストを繰り返す前に、`bun scripts/drop-test-schemas.ts` で蓄積したテスト schema を削除できます。

コンテンツイベントやマップ更新は、対応する `tests/canon-events.test.ts`、`tests/novel-events.test.ts`、`tests/mainline-continuation.test.ts`、`tests/momozono.test.ts` も実行します。コミュニティ、画像、知識、検索にはそれぞれ同名のテストがあります。外部の実 API に対する live audit はクォータを消費する可能性があるため、隔離したセーブデータで明確にオンデマンド実行すべきです。モックテストの通過は、すべてのモデルの文体や SD の画質が目視検証済みであることを意味しません。

## 画像アセットの場所

- `content/assets/`: キャラクター立ち絵、アバター、シーン、イベント CG、および Editor の素材ライブラリで管理できる正式なゲームコンテンツ。
- `web/public/assets/`: 固定 UI／ブランドアイコンや AI 能力チェックなどのフロントエンドシステムアセット。例: LINE、Twitter のアイコン、`check img.png`。
- `web/public/favicon.svg`: サイトの favicon。Vite の公開ファイル慣例に従い、public ルートに保持します。
- プレイヤーのアップロードおよび生成画像は、プレイヤーデータディレクトリ内の `uploads/` に保存され、正式なコンテンツアセットに書き戻してはいけません。

画像を追加する前に、それがゲームコンテンツかシステム UI かを判断します。同種のアセットは同じ場所に置き、プログラムの参照、素材記録、ライセンス／出典の説明も同期して更新します。

内蔵シーンと公式ロケーション画像は元の PNG を保持し、隣には品質 88 の同名 JPEG 表示版があります。`web/lib/scene-images.ts` は、列挙された内蔵シーンのみ表示版へ切り替えます。プレイヤーがアップロードした素材は書き換えられません。これらの元画像を更新するときは同名の JPEG も作り直し、そのファイルのリストも同期して保守します。切り替え時の黒画面は、次の背景とキャラクター立ち絵のデコード完了を待ちます。読み込み試行ごとに 30 秒の安全上限を設け、表示版が失敗したときは元画像へフォールバックします。作者素材ルートは 1 時間のキャッシュと ETag を提供し、素材内容が更新されるとブラウザは再検証します。

## コンテンツのアップグレードと安定識別子

`core/story.ts::upgradeStories` は、既存テキストの修復、キャラクターストーリーの修復、第1〜3巻の題材、第4〜9巻の導入、桃園中学校、本編接続、小説書目、公衆ロケーションパックを順に処理します。各パックは `storyPacks` で一度限りとしてマークされるため、以後は Editor での削除・編集を尊重すべきです。イベントやロケーションを追加する前に、前提、日付、学年、シーン画像、旧セーブデータのパスを確認します。

イベント ID、ロケーション ID、キャラクター ID、コミュニティアカウント ID は永続的な参照であり、単なる UI 文字列ではありません。改名時は、作者コンテンツ、進行中の location／対応待ちデート、関係テーブル、投稿者／メンション、テストを同期して処理する必要があります。画面の名前や @handle を変えるだけでは不十分です。既存の `gusto-kaimei` → `gusto-hashira` ロケーション修復は `core/official-places.ts` を参照できます。新しい移行では、既存のプレイヤーデータを明確に保護すべきです。
