## 結論

そのリクエスト身分、永続イベント、ツール実行契約、モデル適応、コンテキスト整理の方法を参考にする価値があります。既存の Bun／SQLite 上に段階的に実装するのがよく、Cordis プラグイン構築全体を持ち込む必要はありません。公式 README は developer preview と明記しており、互換性のない変更がある可能性があります。

保持する制約：SD／検索はオフにできる。LINE とストーリーは独立。LLM がツールを呼ぶかどうかを決定。API の時間上限は追加しない。ゲームデータと公開可能コンテンツは分離。Harness の timeoutMs オプションをゲームが必ず採用するポリシーとして扱わない。

## 1. リトライをまたぐリクエスト識別を優先して追加

上流の根拠：`packages/api/session-controller/README.md` の requestId／rpcId、pending submission、既存の acceptance 再利用の契約。

本ゲームには既にフロントエンドのボタンロック、runId、sceneRevision がありますが、`server/game-api.ts` には requestId の重複排除がありません。リクエスト完了後にレスポンスがネットワークで失われると、プレイヤーのリトライが別のリクエストとして扱われます。

提案：フロントエンドが最初の送信で requestId を生成し、リトライでは同じ ID を使い回す。SQLite は `(owner, runId, requestId)` の一意制約で、入力サマリ・作業状態・結果を保存します。同じ ID で入力が異なる場合は拒否。同じ ID かつ同一入力なら元の作業または結果を返します。ゲーム状態更新と作業完了記録は同じトランザクションに入れます。

外部 SD が冪等キーをサポートしない場合、プログラムがクラッシュしても「ちょうど一度」の遠隔生成は保証できません。遠隔結果が不明な場合は unknown とし、クエリと手動リトライの入口を残し、自動再送はしません。

受け入れ：二重ページで同じ ID を同時送信、送信成功後の切断リトライ、同じ ID で異なる入力、生成中の読み込み／新規ゲーム、プログラム再起動後の元結果のクエリ。

## 2. 永続イベントで LINE と作業状態を配信

上流の根拠：`docs/architecture.md` の durable Session events と transient Agent events。`packages/api/session-controller/README.md` の follow、seq、再接続補完。

本ゲームには独立したバックグラウンド LINE、未読状態、画像生成記録が既にありますが、UI は依然 1.5 秒ごとにクエリしています。`server/timings.ts` はプログラム内統計の直近 100 件だけを保存し、完全な作業経過を再構築できません。

提案：SQLite の append-only イベント。各項目に owner、runId、requestId、seq、type、payload を持ちます。単一の SSE チャネルで line.received、image.queued、image.started、image.completed などのイベントを配信。クライアントは seq で重複排除し、切断後は最後のカーソルから補送します。出力中の文字は一時的でよく、完了済みメッセージは必ず先に永続化します。カーソルが古すぎる場合はスナップショットを返し、カーソルをリセットします。

受け入れ：切断補送で漏れ／重複なし、遅いクライアントが生成を妨げない、読み込み後に古いイベントが新規ゲームを汚染しない、受信でタイプライターをリセットしない。記録の保持とイベントのページングを考慮し、すべてのメモリ全文を通知に重複して含めない。

## 3. ツール入口を小さな registry に統一

上流の根拠：`docs/subsystems/tools.md` と `packages/core/tools/src/index.ts` の schema、execute、canonical output、concurrency メタデータ、キャンセル契約。

現在、キャラクター、ストーリー、検索、SD はそれぞれ別々にツール入力を解析しています。一貫したツール定義（名前、有効化条件、入力検証、結果検証、execute、安全に並行できるか）を確立し、ドメイン規則は各モジュールに残すことを提案します。

ツール一覧はその時点で利用可能な機能だけを含めます。SD をオフにしたときは画像ツールを登録しません。ツールが存在しない、引数エラー、サービス失敗、プレイヤーキャンセル、結果不明は区別可能な結果にします。ツール実行の結果が確認されてから、画像が送信されたと主張します。安全な知識クエリは並行実行可能。同じ SD サービスはキューのまま維持します。

受け入れ：プラグイン無効時はネットワークリクエストなし。任意の LLM ツール名／JSON で状態が壊れない。失敗後もキューを継続できる。キャンセルが実行中の作業を早期に解放しない。

## 4. 真のコンテキスト予算と遡及可能な要約を追加

上流の根拠：`docs/subsystems/compaction.md` の pressure／context-overflow、ソース序数、要約置換トランザクション、失敗時は元内容を置き換えない。

現在、重要メモリには日付と根拠がありますが、`core/engine.ts::compactMemory` の summary は文字列連結後に末尾を切るだけで、archive は 200 件しか保持しません。これは前回の改善後も残る制限です。

提案：元の会話イベントを保持し、そのリクエスト用の context view を生成します。取得できるモデル容量と推定 token から予算を計算し、キャラクター設定、現在日付／時間帯、最近の完全な会話、関連重要メモリを優先的に保持します。低優先度コンテキストだけを要約します。要約にはソースイベント ID、バージョン、カバー範囲を付け、成功検証後にのみ入力ビューを置き換えます。要約が失敗しても元の記録に戻れます。まず確定した予算での削減と検索を実装し、その後に LLM 要約を追加します。

受け入れ：日をまたぐメモリを今日と誤認しない。重要事項が遡及可能。要約失敗でデータを失わない。コンテキストオーバーフローで同じ巨大プロンプトを盲目的に再送しない。ツール呼び出しと結果を分断しない。

## 5. モデル適応と構造化エラー

上流の根拠：`docs/subsystems/llm-streaming.md` の adapter、モデルコンテキスト情報、ストリーミング語彙、provider retry policy。`docs/agent-lifecycle.md` の step／attempt／settlement。

散らばった endpoint の組み立て、tool-call デコード、usage、finish_reason、モデルエラーを共通適応層に集約します。当面は現在の OpenAI 互換プロトコルを維持し、DeepSeek モデルには固定しません。モデル一覧はヒントとして提示し、一覧にないモデルを手動入力するのを妨げません。

区別：認証／引数エラー、レート制限、コンテキスト過長、出力の切り詰め、ユーザーキャンセル、転送結果不明。リトライは操作の意味論に沿い、requestId を使い回します。リトライ回数、出力 token 予算、API タイムアウトを混同しない。requestId で各ステップの所要時間を連続させ、鍵やマスクされていないヘッダーを保存しない。

## 推奨実装順序

1. requestId と作業状態のトランザクションで、まず重複副作用をなくす。
2. 永続イベントと SSE で、LINE のポーリングを置き換え、補送に対応。
3. ツール registry とモデル適応で、既存モジュールの実行契約を統一。
4. コンテキスト予算・ソース検索・要約。品質は別途、長編プレイサンプルで検証。

これは本ゲームのソースに基づく設計提案であり、適用済みの機能ではなく、上流をそのまま取り込めば上記の保証が得られるという意味でもありません。

## 実装済みの第一版 Harness

以下は後続の実装更新であり、上記提案における「未実装」状態を置き換えるものです。

- `server/harness-request.ts`：永続 requestId、入力要約、同一リクエストのマージ、完了結果の再生、結果不明時の自動再送拒否。状態のコミットとリクエストの settlement は同じ SQLite トランザクション。ストリーミングのオブザーバーが切断しても、引き継いだ作業はキャンセルしない。
- `server/harness-events.ts`：永続イベント序数、単一 SSE、Last-Event-ID 補送、プレイヤーごとに直近 10000 イベントを保持、古すぎるカーソルはスナップショット同期を要求。LINE の固定ポーリングは削除済み。手動画像は作業結果クエリを待機／復旧機構として残す。
- `server/tool-registry.ts`：画像生成、知識読み取り、能動 LINE が共通の入力／結果検証と実行入口を使用。キャラクター／ストーリー出力は元の専用検証器を残し、セリフ・ナレーション・選択肢の規則を弱めない。
- `server/model-runtime.ts`：チャット、ストーリー、知識、検索判断、画像生成判断で共通のモデル転送とエラー分類を使用。既定 65536 token の調整可能な推定予算、システムと今回の入力を保持、古いツール交換をまとめて除去、外部リクエストの自動再試行はしない。
- `server/memory-view.ts`：モデル用にソース ID を持つ関連重要メモリを選別。リセント領域から外れた元の記録はプレイヤー SQLite に別途保存し、prompt の削減とともに消えない。この版は決定的な検索／削減を使用しており、LLM 意味要約を完了したとは主張せず、推定値をモデル公式 tokenizer とも主張しない。
- 新規 `tests/harness.test.ts`：重複排除、衝突、再起動後の結果不明、原子的コミット、読み込み隔離、イベント再生、ストリーミング切断、ツール無効化、モデルエラーを網羅。

互換性：requestId を持たない旧クライアントも引き続き使用可能。新クライアントはすべてのゲーム操作に requestId を付けます。サーバー再起動後に確認できない遠隔 SD 作業は再送しません。既存セーブは追加されたデータテーブルに自動適応します。ソースは本プロジェクトの要件に合わせて独自実装しており、dsh runtime を取り込んだり起動したりはしていません。

まだ完了を主張していないもの：公式 Harness の完全なプラグインツリー、モデルの正確な tokenizer、LLM 意味要約、外部 SD のプロセスをまたぐちょうど一度。テストは `tests/harness.test.ts`。新機能は、その request settlement、イベント補送、データ保存が本当にこれらの契約を踏襲しているかを先に確認すべきであり、この研究文書の提案を引用するだけでは不十分です。
